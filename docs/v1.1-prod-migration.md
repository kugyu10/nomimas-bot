## 2. 適用直後に見るべき観測点

1. **`cron.job` に登録されたか**
   ```sql
   select jobid, jobname, schedule, active
   from cron.job
   where jobname = 'twipla-scrape-poll';
   ```
   `schedule = '*/15 * * * *'`, `active = true` の1行が返ること。

2. **`cron.job_run_details`（発火して成功しているか）**
   ```sql
   select start_time, status, return_message
   from cron.job_run_details
   where jobid = (select jobid from cron.job where jobname = 'twipla-scrape-poll')
   order by start_time desc
   limit 10;
   ```
   `status = 'succeeded'` が続くか、最初の1〜2回で `failed` が出ていないかを見る。

3. **`net._http_response`（scraperへのPOSTが実際に届いて2xxを返しているか）**
   ```sql
   select id, status_code, timed_out, created
   from net._http_response
   order by id desc
   limit 20;
   ```
   `status_code = 200` が中心であること。`timed_out = true` や 4xx/5xx が続く場合は
   Vaultのシークレット不整合（0節1点目）か scraper 未デプロイ（0節2点目）を疑う。

4. **`participants.scraped_at` が更新されているか**
   ```sql
   select event_platform_url_id, max(scraped_at) as last_scraped
   from public.participants
   group by event_platform_url_id
   order by last_scraped desc
   limit 10;
   ```
   ポーリング対象イベントの `event_platform_url_id` について、直近15分以内の
   `last_scraped` が増えていくこと。

5. **`notification_logs` に `kind = 'scrape_changes'` が増えているか**
   ```sql
   select created_at, event_id, kind, recipients, sent, failed, skipped_no_line_id, detail
   from public.notification_logs
   where kind = 'scrape_changes'
   order by created_at desc
   limit 10;
   ```
   実際に参加者の増減・ステータス変化が起きたタイミングで行が増えること
   （変化が無いポーリングは通知をスキップする仕様なので、行が増えないポーリングがあっても異常ではない）。

## 3. ロールバック手順

```sql
select cron.unschedule('twipla-scrape-poll');
```

これだけで即時にジョブが停止する。

**安全である理由**:
- 本マイグレーションはテーブル定義・既存データを一切変更しない
  （`cron.schedule` の登録・`do $$ ... $$` による存在チェックのみ）。
- `cron.unschedule` は `cron.job` から該当ジョブの行を削除するだけで、
  `participants` / `notification_logs` 等のアプリケーションデータには触れない。
- 既存の `confirm-broadcast-daily`（jobname が異なる）には一切影響しない。
- ロールバック後に再度有効化したい場合は、同じマイグレーションSQL
  （`select cron.schedule('twipla-scrape-poll', ...)` の部分）を再実行すればよい
  （`schema_migrations` の version 行は残ったままでよく、削除不要 — cron.job の状態と
  マイグレーション台帳は独立している）。

## 4. prod特有の注意: 最初は `active = false` で入れる選択肢

このマイグレーションを適用すると、prodの実イベントに対して実際にTwiplaへのHTTPリクエストが
15分ごとに走り始める。様子を見ながら有効化したい場合は、適用直後に以下を実行して
一時的に無効化できる（ジョブ自体は登録されたまま、発火だけ止める）。

```sql
select cron.alter_job(
  (select jobid from cron.job where jobname = 'twipla-scrape-poll'),
  active := false
);
```

再度有効化する場合:

```sql
select cron.alter_job(
  (select jobid from cron.job where jobname = 'twipla-scrape-poll'),
  active := true
);
```

`cron.alter_job` は `jobid`（bigint）を第一引数に取るため、`jobname` から都度 `jobid` を
サブクエリで引く。`cron.unschedule` によるロールバック（3節）とは異なり、ジョブ定義自体は
消えないので、`cron.job` の行を見ればスケジュール内容はいつでも確認できる。

運用判断: 0節のチェックリスト（Vaultシークレット・scraperデプロイ済み）が全て確認できていれば
`active=false` を経由せずそのまま有効な状態で適用してよい。不安があれば
「適用 → `active=false` → 2節の観測点をSELECTだけで手動確認 → 問題なければ `active=true`」
の順で段階的に有効化する。
