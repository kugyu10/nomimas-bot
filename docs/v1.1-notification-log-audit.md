# v1.1 notification_logs 監査: 「sent:0が14件」と「本人には届いていた」の矛盾

## 1. 結論

`notification_logs` は **参加者本人への配信を最初から記録していないテーブル**である。本人に届いた
3日前の最終確認配信（`message-sender`）は `notification_logs` に一切書き込みを行わない
（`supabase/functions/message-sender/index.ts` に `notification_logs` への言及なし）。
一方 `notification_logs` に残る14件は **主催者(owner/co-owner)向け通知**（`notifier.ts` の
`notifyConfirmUpdate`/`notifyScrapeChanges`）であり、その受信者テーブル `oa_members.line_user_id`
が未設定（null）だと構造的に `recipients:0`/`sent:0`/`skipped_no_line_id`加算 になる
（`supabase/functions/_shared/notify/notifier.ts:149-152`, `312-315`）。
つまり「別の配信経路（本人向け・未計測）」と「計測されている経路（主催者向け・受信者未設定で空振り）」
を同じ言葉「通知」で混同していたために矛盾に見えていた。両者は完全に独立している。

## 2. `notification_logs` は何を測っているテーブルなのか

### 設計意図（コード内コメントより）

- テーブル定義のコメント: 「notification_logs: 通知発火の機械検証基盤（NOTIF-01）／窓外は行を書かず
  console に件数ログのみ ─ 『2日前より前では通知されない』＝行が存在しないこと」
  （`supabase/migrations/20260611171037_create_core_tables.sql:173-175`）
- `notifier.ts` 冒頭コメント: 「通知本体（受信者解決 → 窓判定 → push → notification_logs 記録）」
  「notification_logs への INSERT は送信実行時のみ（窓外は行を書かない）」
  （`supabase/functions/_shared/notify/notifier.ts:3,12`）

つまりこのテーブルは **「主催者向け通知が、窓内で正しく実行されたか」を機械検証するための計測台帳**
として作られている。窓外なら行自体を作らない、という設計であり、「配信が実際に相手のLINEに届いたか」
の完全な記録ではなく、あくまで **notifier.ts 経由の呼び出しに限定した計測** である。

### 書き込み箇所（全網羅）

`grep -rn "notification_logs" --include="*.ts" --include="*.sql"` で見つかる `.insert(...)` 呼び出しは
以下の3箇所のみ、すべて `supabase/functions/_shared/notify/notifier.ts` 内:

1. `notifyConfirmUpdate` の `oa_members` SELECT 失敗時のエラー行（`notifier.ts:130-142`）
2. `notifyConfirmUpdate` の通常フロー、送信実行後の1行（`notifier.ts:200-212`）
3. `notifyScrapeChanges` の `oa_members` SELECT 失敗時のエラー行（`notifier.ts:289-305`）
4. `notifyScrapeChanges` の通常フロー、送信実行後の1行（`notifier.ts:354-369`）

呼び出し元は2つだけ:

- `supabase/functions/webhook/index.ts:477`（`notifyConfirmUpdate` を `kind: "completion"` で呼ぶ。
  ただし呼び出し条件は「`result.reply === "completion"` かつ回答保存成功かつ値が変化した時」のみ ─
  `webhook/index.ts:465-483`。コメントに「途中回答（answer種別）の都度通知は owner への通知過多に
  なるため廃止」とあり、`kind: "answer"` は現在到達不能な設計上の残骸）
- `supabase/functions/scraper/index.ts:185`（`notifyScrapeChanges` を再スクレイプの差分検出時に呼ぶ）

**CHECK制約**（`supabase/migrations/20260611171037_create_core_tables.sql:179`）:
```sql
kind text not null check (kind in ('answer', 'completion', 'scrape_changes'))
```
許される `kind` は3種類とも **主催者向け通知**（参加者の回答完了を主催者に知らせる／スクレイプ差分を
主催者に知らせる）に対応する値だけである。「本人（参加者）への最終確認配信」を表す `kind` はそもそも
存在しない。

### 測っていないもの（明示）

- **参加者本人への最終確認バンドル配信**（`message-sender/index.ts` が cron/手動で行う初回3バブル送信）
  ─ 後述の通り、このファイルには `notification_logs` への参照が一切ない。
- **webhookの質問リプライ配信**（`replyMessage` による1問ごとの返信、`webhook/index.ts:452`付近）
  ─ これも `notification_logs` とは無関係。
- `kind: "answer"`（途中回答ごとの主催者通知）は制約上は許可されているが、呼び出し元コードが
  `completion` のときしか呼ばないため、実質死んだ経路。

## 3. `sent: 0` / `recipients: 0` になる機構

`notifyConfirmUpdate` / `notifyScrapeChanges` はどちらも同型の分岐を持つ（該当は completion 側で説明、
scrape側は `notifier.ts:279-315` が同型）。

1. **窓外**（`isWithinNotifyWindow` が false）→ 行を書かず return（`notifier.ts:94-99`, `256-261`）。
   → これは14件の中には現れない（窓外なら行自体が存在しないため）。
2. **OA line_channel_id 不一致**（マルチOA運用時のチャネル取り違え防止）→ 行を書かず return
   （`notifier.ts:109-114`, `271-276`）。
3. **`oa_members` SELECT 自体が失敗**（インフラ障害）→ `detail: {recipients_error: true}` 付きの行を
   書いて return（`notifier.ts:126-146`, `285-309`）。recipients/sent/failed/skipped は全部0で埋める。
4. **`oa_members` は取得できたが、対象OAの行の `line_user_id` が全部 null**
   （`recipientMembers = allMembers.filter(m => m.line_user_id != null)` が空配列になる）
   → `recipients = 0`、`skippedNoLineId = allMembers.length`（`notifier.ts:149-152`, `312-315`）。
   この場合 `recipients > 0` の条件を満たさないため push は1件も呼ばれず、`sent = 0`。
   → **これが `sent:0 / recipients:0` かつ `skipped_no_line_id > 0` を同時に生む唯一の「正常」経路**。
5. push は試みたが全件失敗（`recipients > 0` だが LINE API が全部落ちた等）→ `failed = recipients`,
   `sent = 0`, だが `recipients` 自体は0にならない。

観測されているのは「`sent:0` **かつ** `recipients:0`」なので、3(インフラ障害)または4
（`oa_members.line_user_id` が全null）のどちらかである。`skipped_no_line_id` 累計23が14件に分散して
いる（1件あたり平均1.6程度）ことは、3のケース（`skipped_no_line_id` は常に0固定）ではなく、
4のケース（OAごとの owner/co-owner 数がそのまま `skipped_no_line_id` になる）と整合する。
→ **14件はほぼ全て「4: oa_members.line_user_id が該当OAで全null」による構造的スキップ**と推測できる
（推測。DB未確認、後述6参照）。

## 4. 「届いていたのに0」の内訳

- **本人に届いた3日前の最終確認**は `message-sender`（`supabase/functions/message-sender/index.ts`）
  経由。受信者解決は `get_confirm_targets()` RPC が `participants.line_user_id → line_users` を
  JOIN して行う（`supabase/migrations/20260612120000_setup_cron_and_targets.sql:36-40`）。これは
  `oa_members.line_user_id`（主催者の受信先）とは**別のテーブル・別のカラム**。
  `message-sender/index.ts` を全行確認したが、`notification_logs` への `insert`・`select` は
  1回も出現しない。送信結果は関数のレスポンスJSON（`{status, targets, sent, failed, skippedUnlinked}`,
  `message-sender/index.ts:370-379`）としてのみ返り、呼び出し元の pg_cron（`net.http_post` 経由、
  `20260612120000_setup_cron_and_targets.sql:103-125`）はレスポンスをどこにも永続化しない
  （fire-and-forgetな非同期HTTPコール）。
  → **本人に届いた配信はそもそも「計測対象外」であり、ログが0件でも1件でも矛盾ではない。**

- **ログに残っている14件**は `webhook`（参加者が最終質問に回答し `completed` に遷移した瞬間の
  owner/co-owner 向け完了通知）と `scraper`（再スクレイプで新規参加者/状態変化が検出された時の
  owner/co-owner 向けサマリ通知）のいずれか。**「本人が最終確認を受け取った」という事実とは無関係の
  別イベント**を記録している。
  → 「実際に送られなかったのか」という問いには、3(インフラ障害)なら「試みる前に落ちた」、
  4(受信者未設定)なら「push関数自体を1回も呼んでいない（`recipients > 0` の分岐に入らない）」が
  答えになる。どちらにしても**主催者への通知は本当に届いていない**（本人への最終確認とは別物）。

## 5. どう直すか

### 案A: `message-sender` の配信結果も `notification_logs` に記録する

CHECK制約に新しい `kind` を追加するマイグレーション断片（イメージ、要レビュー）:
```sql
alter table public.notification_logs
  drop constraint notification_logs_kind_check;
alter table public.notification_logs
  add constraint notification_logs_kind_check
  check (kind in ('answer', 'completion', 'scrape_changes', 'confirm_sent'));
```
`message-sender/index.ts` のループ末尾（`sent++`/`failed++` の集計後、6番セクション終わり
`index.ts:366`付近）で1回（バッチ全体で1行、対象ごとではない）まとめてINSERTする形が
既存の「1スクレイプ=1サマリ通知」方針（`notifier.ts:18`）と一貫する。
- 利点: 「主催者向け」と「参加者向け」の両方が同じ台帳で見えるようになり、今回のような
  「ログはゼロなのに届いていた」という混乱が起きなくなる。既存テーブル・既存の管理画面クエリを
  再利用できる。
- 欠点: `notification_logs` の意味が「主催者向け通知の検証台帳」から「全配信ログ」に変わるため、
  既存のRLSポリシー（`notification_logs_oa_member_select`,
  `supabase/migrations/20260611171038_enable_rls.sql:398-402`）や既存テスト
  （`admin/tests/integration/rls.test.ts:659-`, `supabase/functions/tests/e2e_full_chain_test.ts`
  の複数箇所）が前提を壊されるリスクがある。`participant_id` 1行=1参加者の粒度とバッチ1行=N参加者
  の粒度が混在し、`recipients`/`sent`/`failed` の意味がkindごとに変わってしまう。

### 案B: 送信ログ専用の別テーブルを作る（例: `confirm_send_logs`）

- 利点: 主催者向け検証台帳（`notification_logs`）の既存の意味・RLS・テストを一切変えずに済む。
  参加者向け配信専用のスキーマ（`participant_id`, `pushed_at`, `success`）を素直に設計できる。
- 欠点: テーブルが増え、「通知の状況を見る」ために2つのテーブルを見る必要が出る。運用者が
  混乱しやすい構造は変わらない（見る場所が分かれるだけ）。

### 案C: `oa_members.line_user_id` を埋めて主催者通知を実際に届かせる

- これは「ログの見え方」の問題ではなく、**主催者自身が完了通知/差分通知を一度も受け取れていない**
  という別の実害。`oa_members.line_user_id` を主催者向けに設定するUIやフローは admin 側のどこにも
  見当たらなかった（`admin/components/events/linking-tab.tsx` 等の line_user_id 関連ファイルはすべて
  **参加者**の紐付けUIであり、`oa_members` を更新するコードは admin に存在しない ─
  `grep -n "oa_members" linking-tab.tsx lib/actions/linking.ts lib/data/participants.ts` は無出力）。
  現状 `oa_members.line_user_id` を設定できる経路は `scripts/setup-dev.ts`（開発専用スクリプト、
  dev固定値を直接UPDATE）しかない。
- 利点: 主催者自身も「参加者が完了しました」「新規参加者を検知しました」の通知を実際に受け取れる
  ようになる。
- 欠点: これは通知の**受信**を直す話であり、`notification_logs` の**観測の矛盾**そのものを解決する
  ものではない。かつ「主催者が自分のLINE userIdをどう入力するか」の運用フロー（本人確認込み）を
  新規に作る必要があり、v1.1の主眼（Twiplaポーリング）とはスコープが異なる。

### 推奨

**案B（専用テーブルを新設）を推奨する。** 理由:
- `notification_logs` は既にRLSポリシーとE2Eテストが「主催者向け検証台帳」という意味に強く紐づいて
  おり（`enable_rls.sql:398-402`、`e2e_full_chain_test.ts` の複数assert）、案Aで意味を混ぜると
  既存の検証基盤(NOTIF-01)自体の信頼性を損なう。
- 「参加者に何を送ったか」と「主催者に何を通知したか」は元々別の関心事であり、テーブルを分けた方が
  将来の集計・監視（例:「配信失敗率」を見るダッシュボード）も作りやすい。
- 案Cは並行してやるべきだが、これは「観測の矛盾」の修正ではなく別の不具合（主催者が通知を受け取れて
  いない）の修正なので、優先度と担当を分けて扱うべき。

「朝に本人が判断すべきこと」:
- 主催者（自分）が `oa_members.line_user_id` を設定していない状態を許容するか、それとも次の
  マイルストーンで「主催者オンボーディング時にLINE userIdを紐付ける」フローを作るか（案C）。
- 案Bの新テーブルを作るか、それとも「主催者向け通知はいまのところ運用上使っていないので直さない」
  と割り切って `notification_logs` はそのまま「死んでいる検証台帳」として放置するか。
- v1.1でTwiplaポーリング作業を優先するなら、このIssueは「既知の欠陥・後回し」として明文化して
  残すだけでも十分か。
