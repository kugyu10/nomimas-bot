# v1.1 ポーリング設計（叩き台）

**要約**: スクレイパーが cron に載っておらず参加者取り込みが手動依存のため、直前参加者が最終確認の対象から漏れる。新規 Edge Function `poll-events` を新設し、既存 `_shared` の差分・通知ロジックを直接呼ぶ設計を推奨する。ポーリング間隔はイベント接近度に応じて30分/2時間の2段、対象は「終了済み」と「confirm_days_before + notify窓の外」を除外する。

---

## 1. 何が問題か

- 現行 cron は `confirm-broadcast-daily`（`0 1 * * *` = JST 10:00、`message-sender` を叩くのみ）が唯一の定期実行で、参加者取り込み（スクレイプ）は cron に一つも載っていない（`supabase/migrations/20260612120000_setup_cron_and_targets.sql:103-130`）。
- 参加者の取り込みは管理画面の「取得」ボタン（手動 POST → `scraper` Edge Function）に依存している（`supabase/functions/scraper/index.ts:16-63`）。
- そのため、管理者が最後に「取得」を押した後に Twipla 上で新たに参加表明した人は `participants` テーブルに入らず、`get_confirm_targets`（`status='attending' AND confirm_status='pending'`, `supabase/migrations/20260612120000_setup_cron_and_targets.sql:53-55`）の対象にもならない。直前参加者ほど最終確認が届かない構造的な欠陥になっている。
- 自動ポーリングを入れれば、この「直前参加者に届かない」問題は取り込みタイミングの問題として解決できる。

---

## 2. ポーリングの設計

### 2.1 どこでイベントを列挙するか

**案A: cron本体のSQLで `event_platform_urls` を走査し、`net.http_post` で `scraper` を対象ごとに叩く**

既存の `confirm-broadcast-daily`（`supabase/migrations/20260612120000_setup_cron_and_targets.sql:103-130`）と同じ「cronジョブ本体にVaultシークレット名参照だけで完結するSQL」を書くパターン。cron本体を `select ... from event_platform_urls` のサブクエリで複数行にし、行ごとに `net.http_post` を呼ぶ形になる。

- 利点: 新しい Edge Function の追加・デプロイが不要。既存の「Vault参照のみ・URL/キーをリテラルで書かない」流儀をそのまま複製できる。
- 欠点:
  - `net.http_post` は非同期発火（`net._http_response` テーブルに後で結果が入る方式）で、SQL側からは「投げた」時点までしか見えず、レスポンスを見て次の処理を分岐させることができない。
  - リトライ・エラーハンドリング・イベント間の待機（Twiplaへの負荷分散）をSQL/pg_cronだけで書くのは煩雑（`DO $$ ... $$` ブロックで手続き的に書く必要があり、既存マイグレーションのシンプルな宣言的スタイルから外れる）。
  - 同時多重発火の制御（1回のポーリングで何件まで、何秒間隔で叩くか）をSQLで表現しづらい。
  - 観測性: `cron.job_run_details` と `net._http_response` を跨いで確認する必要があり、ログが分散する。

**案B: 新しい Edge Function（`poll-events`）が対象URLを列挙して自分で回す。cronは1回叩くだけ**

- 利点:
  - TypeScriptで「対象を絞る→優先度順に並べる→間隔を空けて順次処理→失敗はログして継続→件数を集約してレスポンス」という手続き的な制御が自然に書ける（既存の `message-sender` が同じ形で複数対象を順次処理している: `supabase/functions/message-sender/index.ts`）。
  - `scraper/index.ts` が既に持っている差分計算・通知ロジック（`diffParticipants` / `notifyScrapeChanges`）を `_shared` 経由でそのまま再利用できる。
  - cron本体は「1回 `poll-events` を叩くだけ」で済み、既存の `confirm-broadcast-daily` と全く同じ形（Vault参照＋`net.http_post`＋`timeout_milliseconds`）を複製すればよい。
- 欠点: 新規 Edge Function 1つのデプロイ工数が発生する（一度だけ）。

| 観点 | 案A（cron SQLで直接列挙） | 案B（`poll-events` Edge Function） |
| --- | --- | --- |
| デプロイの手間 | 追加デプロイ不要 | 新規Function 1つを一度だけデプロイ |
| 観測しやすさ | `cron.job_run_details` + `net._http_response` に分散 | Function内のログ + レスポンスJSONに集約 |
| 失敗時のリトライ | SQLで書くと煩雑（`DO $$ $$` が必要） | try/catchで1件失敗しても次に進みやすい |
| タイムアウトの効き方 | `net.http_post` 単位の `timeout_milliseconds` のみ | Function全体の実行時間制約と、各fetchの `AbortSignal.timeout` を両方考慮できる |
| Twiplaへの同時接続数制御 | SQLでは間隔・順序の制御が難しい | `await` の直列処理・待機で自然に制御できる |

**推奨: 案B。**

理由: 2.4節（Twipla負荷配慮）と2.5節（間隔のtiering）で必要になる「イベントごとに直前だけ密に・遠いものは疎に」という条件分岐や、失敗時にログを出しつつ次のイベントに進む継続処理は、SQLだけで書くと複雑さが跳ね上がる。デプロイ工数は一度きりであり、運用中の変更容易性（間隔の数値調整、対象条件の調整）を優先すべき。

**実装上の追加提案（設計、現状のコードには無い）**: `poll-events` は HTTP で `scraper` を呼び出すのではなく、`scraper/index.ts:65-208` にある「`event_platform_urls` 照合 → upsert → 差分計算 → `notifyScrapeChanges`」の一連の処理を `_shared/scrape/run.ts`（新設）のような共通関数に切り出し、`scraper`（単発URL・管理画面向け）と `poll-events`（複数URL・cron向け）の双方から呼ぶ形にする。HTTP経由にすると `scraper` はデフォルトで JWT 検証が有効（`supabase/config.toml` には `[functions.webhook] verify_jwt = false` しかなく、`scraper` 用のセクションは無い＝デフォルトの `verify_jwt=true`）なので `poll-events` から呼ぶ際にJWT発行が絡むが、直接関数呼び出しにすればその手間自体が発生しない。

### 2.2 ポーリング間隔

前提事実:
- 既存の通知窓 `isWithinNotifyWindow`: `event_date - 2日 <= today <= event_date`（`supabase/functions/_shared/notify/window.ts:26-30`）。
- `confirm_days_before` はイベントごとに設定可能で default 7（`supabase/migrations/20260611171037_create_core_tables.sql:53`）。`get_confirm_targets` はこの値を使い `event_date - today <= confirm_days_before` の窓でイベントを絞る（`supabase/migrations/20260612120000_setup_cron_and_targets.sql:56-65`）。

推奨案: **単一の cron を高頻度（30分間隔）で走らせ、`poll-events` 内部でイベントごとの「必要な間隔」を判定してスキップする**設計にする。複数の cron スケジュールを間隔ごとに用意するより、1本の cron + アプリ側のtiering判定の方が管理対象が減る。

```sql
select cron.schedule(
  'poll-events-every-30min',
  '*/30 * * * *',   -- 30分おき（JST/UTCどちらでも同じ間隔）
  $$ ... 既存パターンと同じ Vault参照 + net.http_post ... $$
);
```

`poll-events` 内部のtiering判定（推奨値）:
- イベント当日〜2日前（通知窓内、`event_date - today <= 2`）: 30分ごと（cronの実行間隔そのまま＝毎回ポーリング対象）
- それより先、`confirm_days_before` の窓内（`2 < event_date - today <= confirm_days_before`）: 2時間ごと
- 上記いずれにも当たらない（窓外）: 対象外（2.3節）

「前回いつポーリングしたか」は新しい列を増やさず、既存の `participants.scraped_at` の `event_platform_url_id` ごとの最大値を使う（`scraper/index.ts:107` で毎回 upsert 時に書き込まれている値）。一度もスクレイプされていない（`max(scraped_at) is null`）イベントは無条件で対象にする。

```sql
-- poll-events が実行すべき対象を選ぶクエリの骨子（イメージ）
select epu.id, epu.url, e.event_date, e.confirm_days_before,
       max(p.scraped_at) as last_scraped
from event_platform_urls epu
join events e on e.id = epu.event_id
left join participants p on p.event_platform_url_id = epu.id
where e.event_date >= (now() at time zone 'Asia/Tokyo')::date
  and (e.event_date - (now() at time zone 'Asia/Tokyo')::date) <= greatest(e.confirm_days_before, 2)
group by epu.id, epu.url, e.event_date, e.confirm_days_before
having max(p.scraped_at) is null
   or now() - max(p.scraped_at) >= (
        case when (e.event_date - (now() at time zone 'Asia/Tokyo')::date) <= 2
             then interval '30 minutes'
             else interval '2 hours'
        end
      )
order by max(p.scraped_at) asc nulls first
limit 20;
```

（このクエリは `poll-events` の中で `supabase.rpc` か生SQL相当として実行するイメージ。実装時は Supabase JS クライアントの `.rpc()` 用関数として切り出すか、`poll-events` がPostgRESTのフィルタで同等条件を組み立てる。`greatest(confirm_days_before, 2)` は `confirm_days_before` が2未満に設定された場合でも通知窓をカバーするための安全策。）

### 2.3 対象イベントの絞り方

- **終了済みイベントを叩き続けない**: `e.event_date < today` を除外する。上記クエリの `where e.event_date >= (now() at time zone 'Asia/Tokyo')::date` がこれに相当（`get_confirm_targets` の既存条件 `supabase/migrations/20260612120000_setup_cron_and_targets.sql:63` と同じ書き方に揃えている）。
- **まだ遠い将来のイベント**: `confirm_days_before`（と通知窓2日）を超えて先のイベントはポーリング対象に入れない（`(e.event_date - today) <= greatest(confirm_days_before, 2)`）。取り込み自体を止めるのではなく「まだ自動で急いで取りに行く必要がない」という判断。管理画面の手動「取得」ボタンは従来通りいつでも使える。
- この2条件で、「終了済み」と「まだ先」の両方を除外し、実際に確認配信に関わる窓だけをポーリング対象にする。

### 2.4 Twiplaへの負荷配慮

- **1回のポーリングでの最大リクエスト数**: 上記クエリの `limit 20` を上限とする（poll-events 1回の呼び出しで最大20イベント）。登録イベント数がこれを超える運用になった場合は要見直し（4節「未解決の論点」）。
- **イベント間の間隔**: `poll-events` 内でURLを1件ずつ **直列**に処理し、各リクエストの間に1〜2秒の待機を入れる（同時並列fetchはしない）。既存 `twiplaProvider.fetchParticipants` は1リクエストごとに `AbortSignal.timeout(10_000)`（10秒）を持つ（`supabase/functions/_shared/providers/twipla.ts:131-134`）。
- **User-Agent**: 現状 `twiplaProvider.fetchParticipants` の `fetch()` 呼び出しには `headers` の指定がなく、User-Agentは Deno のデフォルト値のまま（`supabase/functions/_shared/providers/twipla.ts:131-134` に headers 指定なし）。ポーリング頻度が上がる以上、識別可能な User-Agent（例: `nomimas-bot-poller/1.0 (+contact-url)`）を付けるべきだが、名乗り方（連絡先を晒すか等）は運用判断が必要（4節）。
- **HTTPエラー・レート制限時の振る舞い**: 個々のURLの `fetch` 失敗（非2xx・タイムアウト・レート制限）は現在の `scraper/index.ts:54-63` と同様に `try/catch` で握り、そのイベントだけスキップしてログを出し、他のイベントの処理は継続する。連続失敗時の指数バックオフ・一時停止は今回のスコープでは実装しない（未解決の論点に回す）。
- **1イベントあたりの最短ポーリング間隔**: **30分に1回まで**（2.2節のtier1）。これより短くしない。

### 2.5 離脱者（declined化）の扱い

事実確認: `confirm_status` を `status`（attending/interested/declined/unknown）の変化に応じて自動更新するコードは現状どこにも存在しない（`grep -rn "declined" supabase/functions/` でスクレイパー由来のstatus値以外にヒットなし）。`get_confirm_targets` は `status='attending' AND confirm_status='pending'` のみを対象にする（`supabase/migrations/20260612120000_setup_cron_and_targets.sql:53-55`）。

- **attending → declined になった人**: `confirm_status` はそのまま変更しない。`get_confirm_targets` の `status='attending'` 条件により、次回以降の cron 配信では自然に対象外になる（新たな確認メッセージは送られない）。矛盾なし。
- **既に最終確認を送ってしまった人（`confirm_status` が `sent`/`in_progress`/`completed`）が後から declined になった場合**: 現状のコードでは何もしない。主催者側には `notifyScrapeChanges` の `statusChanges` 経由で「ステータス変化あり」がまとめて通知される（`supabase/functions/_shared/notify/notifier.ts:332-336`, `_shared/notify/diff.ts:42-43`）。参加者本人に「キャンセルを確認しました」等を追加で送る仕組みは今回のスコープに含めない（新しい文面設計が必要になりスコープが肥大化するため）。**推奨: 何もしない（現状維持）。理由: 主催者が通知で気づける状態を作ることを優先し、参加者本人向けの新規メッセージ設計は次段に回す。**
  参考: 別エージェントが同日夜に作成した擬似ポーリングのフィクスチャ・テスト（`supabase/functions/tests/twipla_polling_test.ts`、`supabase/functions/tests/fixtures/twipla_poll_t0〜t3.html`）で、attending→declined（t1→t2）・declined→attending（t2→t3）のいずれも `diffParticipants` が `statusChanges` として正しく検出することが実行確認済み（5 passed / 全体117 passed）。つまり主催者への `statusChanges` 通知は、どちらの方向の遷移でも既に機能する前提に立てる。
- **declined → attending に戻った人に再度確認を送るか（`confirm_status` のリセット是非）**: `get_confirm_targets` は `confirm_status='pending'` のみを見るため、一度 `sent`/`completed` まで進んだ人は自動では再送されない。
  - 選択肢A: declined→attending の遷移を検知したら `confirm_status` を `pending` にリセットし、再度確認フローに乗せる。ただし現状のスクレイパーにもこのUPDATEロジックは無く、新規実装が必要。
  - 選択肢B: リセットしない。既に管理画面には「個別送信」機能があり、`confirm_status` を無視して1名だけ送り直せる（`supabase/migrations/20260614120000_add_participant_confirm_target.sql` の `get_participant_confirm_target` / `message-sender/index.ts` の個別送信モード、`answers` を削除して1問目からやり直す実装込み）。
  - **推奨: 選択肢B（自動リセットしない）。** 理由: (1) 既存の「個別送信」機能で運営が手動カバーできる。(2) 「離脱表明→また参加に戻る」を繰り返す操作で確認メッセージが自動的に何度も再送される事故を避けられる。(3) スクレイプ/ポーリング側に確認フローのstate machine（D-05）を書き換える副作用を持たせず、既存の責務分離（取り込みは取り込み、配信状態管理は別）を保てる。

### 2.6 誤検知で通知を撃たない設計

- **初回スクレイプでの誤通知防止**: `diffParticipants` は既存行が0件のとき全員を「新規」と判定する（`supabase/functions/_shared/notify/diff.ts:29-30, 38-41`）。呼び出し側の `scraper/index.ts:159-162` が `existingRows.length === 0` の場合に通知自体をスキップする実装が既にある（コメントにも "初回スクレイプ: 全員が「新規」になるため通知スキップ" と明記）。`poll-events` が `_shared` の同じ関数を直接呼ぶ設計（2.1節の推奨）を採れば、このガードはそのまま効く。HTTP経由で `scraper` を呼ぶ設計でも同様に効く。
- **パースが失敗して参加者0件になったときの「全員が消えた」誤検知への防御**:
  - 現状のコードを確認した結果、`diffParticipants` は `incoming`（今回の取得結果）を軸にループし、`before`（既存）に存在して `incoming` に存在しない要素は一切参照しない（`supabase/functions/_shared/notify/diff.ts:38` の `for (const p of incoming)`）。つまり「既存参加者が消えた」という概念自体がこの関数に無く、「全員が退会した」という誤通知は構造的に発生しない。
  - また `scraper/index.ts` の upsert 処理には DELETE 文が存在しない（確認済み）。パース失敗で `result.participants` が0件になっても、upsert する行が0件になるだけで既存の `participants` 行は削除されない。DBが「全員消滅」と誤認することもない。
  - 一方で新たなリスク: ポーリング頻度が上がると、Twipla側のHTML構造変化などによる「パース失敗で0件」が単発の手動実行時より頻発しうる。DBは壊れないが、静かに空振りが続いて気づきにくくなる。
  - **提案（現状には無い、新設計）**: `poll-events` は「取得結果が0件」かつ「その `event_platform_url_id` に既存の `participants` 行が存在する」場合に WARNログを出す（upsertの挙動自体は変えない）。同一URLで連続N回（例: 3回）0件が続いた場合の管理者アラートは、今回のスコープでは実装せず未解決の論点に回す。

## 3. 段階的な導入手順

**dev で確かめる → prod に当てる**の順で進める。prod適用は朝に本人が実行する前提。

### dev

1. 新規マイグレーションファイルを追加する（例: `supabase/migrations/<timestamp>_add_poll_events_cron.sql`）。内容は既存の `20260612120000_setup_cron_and_targets.sql` と同じ流儀（Vaultのシークレット名参照のみ・URL/キーをリテラルで書かない・`net.http_post(... timeout_milliseconds := 30000)`）で `poll-events-every-30min` の `cron.schedule` を追加する。
2. `supabase/functions/poll-events/index.ts` を新規実装する。`_shared/scrape/run.ts`（新設、2.1節）に切り出した共通処理を呼ぶ形にする。`config.toml` には明示的な `[functions.poll-events]` セクションを追加しない（デフォルトの `verify_jwt=true` のままでよい — cronからは既存の `confirm-broadcast-daily` と同じ「anonキーJWT + Vault参照」の経路で叩けるため）。
3. dev DBにマイグレーションを適用する（既存の `db reset` / `migration up` 相当の手順。dev環境限定・本人の安全境界内）。
4. dev環境に `poll-events` をデプロイする。
5. cronの発火を待たず `supabase functions invoke poll-events`（CLI経由、`curl -X POST` は使わない）で直接叩き、レスポンス（対象件数・取得件数・通知件数）を確認する。
6. `select * from cron.job` / `select * from cron.job_run_details order by start_time desc limit 20;`（SELECTのみ）で cron ジョブが登録され正しく `net.http_post` を発火しているか確認する。
7. 参加者が実際に増える／ステータスが変わるケースを、既存の dev データ（またはテスト用イベント）で確認し、2.5節・2.6節の想定通り「通知が過不足なく飛ぶか」「declined者が対象から外れるか」を見る。

### prod（本人が朝に実行）

8. dev での確認が済んだマイグレーションファイルと `poll-events` の実装を、そのまま prod に反映する。**1コマンドで当てられる形**として、以下の2コマンドを1行にまとめておく（既存のリリース手順・prod project ref との整合は本人が確認する前提。具体的な `--project-ref` の値やこれまでの prod 反映コマンドの正確な形は本タスクでは未確認）:

   ```
   supabase db push && supabase functions deploy poll-events
   ```

9. 反映後、`select * from cron.job where jobname = 'poll-events-every-30min';` で登録を確認し、最初の数回の `cron.job_run_details` を見て正常に走っているか確認する。
10. 問題が起きた場合のロールバックは `select cron.unschedule('poll-events-every-30min');` で即時停止できる（既存の `confirm-broadcast-daily` には影響しない）。

## 付記2: ポーリングだけでは塞がらない穴（当日参加者）— 2026-08-25 反証で判明

夜間の反証役（独立した検証プロセス）が、この設計に対して**致命的な反例**を出した。記録して残す。

### 反例

**イベント当日の JST 10:00 以降に参加表明した人には、確認配信が永久に届かない。**

1. 確認配信（`message-sender`）を起動するのは `confirm-broadcast-daily`
   （`0 1 * * *` UTC = **10:00 JST の1日1回**）だけ
   — `supabase/migrations/20260612120000_setup_cron_and_targets.sql`
2. 15分ごとのポーリングは変化を検知して `participants` を更新し、**主催者**に
   サマリ通知を送るだけで、`message-sender` を起動しない
   — `supabase/functions/scraper/index.ts` に `message-sender` の呼び出しは存在しない
3. `get_confirm_targets` の cron モードの窓は
   `e.event_date >= (now() at time zone 'Asia/Tokyo')::date`
   — 同マイグレーション 61-64行付近

→ 当日 10:00 以降に参加表明すると、ポーリングは15分後に検知して DB に取り込むが、
その日の配信はもう終わっている。そして翌日には `event_date >= today` が偽になり窓から落ちる。

### なぜポーリング間隔を短くしても解決しないのか

ボトルネックは**検知**側ではなく**配信を起動する頻度**にある。
ポーリングを5分間隔にしても、配信が1日1回なら当日参加者は拾われない。

### 採った対策

`confirm-broadcast-catchup` を追加（`supabase/migrations/20260825030000_add_confirm_broadcast_catchup_cron.sql`）。

- スケジュール `*/30 0-12 * * *`（pg_cron は UTC。**= JST 09:00〜21:59 の30分ごと**）
- **深夜に走らせない**のが要点。`*/30 * * * *` にすると JST 03:00 に確認配信の LINE が飛ぶ
- 二重送信にならない根拠: `get_confirm_targets` は `confirm_status='pending'` のみ返し
  （20260612120000:54,86）、`message-sender` は push 成功直後に `'sent'` へ更新する
  （`supabase/functions/message-sender/index.ts:373-382`）。
  検証: `scripts/v11/check-no-duplicate-confirm.ts`
- 既存の `confirm-broadcast-daily` は**変更しない**。`scripts/verify-cron.ts` が
  その名前とスケジュールを検証しているため、変えると既存の検査が落ちる

### まだ残る穴（運用判断）

**JST 22:00〜翌 08:59 に参加表明した当日参加者は、依然としてカバーされない。**
イベントが深夜〜早朝開催なら間に合わない。塞ぐなら選択肢は2つ:

- (a) catchup の時間帯を広げる → 深夜に LINE 通知が飛ぶ副作用を受け入れる
- (b) **ポーリングが新規 attending を検知した時点で、その参加者だけに個別配信を撃つ**
  `message-sender` には個別送信モードがある（`supabase/functions/message-sender/index.ts:174`
  付近 — `participant_id` 1名のみ・`confirm_status` 無視）。
  scraper の差分検知（`diffParticipants` の `newParticipants` / `attending` への変化）から
  これを呼べば、検知から数十秒で本人に届く。
  利点: 遅延が最小。欠点: scraper が配信の責務を持つことになり、
  「1スクレイプ=1サマリ通知」という現在の設計方針（`notifier.ts` のコメント）と
  責務が混ざる。また深夜の送信抑制をどこで持つかを決める必要がある。

どちらを採るかは運用判断。**(b) のほうが筋は良いが、深夜抑制の置き場所を決めてから入れるべき。**

## 付記3: catchup ジョブが埋め込んだ二重送信と、その直し方 — 2026-08-25 反証2

付記2 の catchup ジョブ（当初「0-12 時台に30分ごと」）に対して、独立した反証プロセスが
**dev の実物から**次を指摘した。記録して残す。

### 反例

**catchup と既存 `confirm-broadcast-daily` が毎日 UTC 01:00（= JST 10:00）に同一分で同時発火し、
同じ参加者に確認配信が2通届く。**

- 「30分ごと」の指定は分 {0, 30} を含む → 時 {0..12} との組で **UTC 01:00 を含む**。
  `confirm-broadcast-daily` は `0 1 * * *` = UTC 01:00。完全に一致。
- pg_cron の解釈は UTC（dev 実測: `current_setting('TimeZone')='UTC'`、
  `cron.job_run_details` の daily の `start_time` は73件すべて 01:00 UTC）
- 2本のジョブ本文は **md5 一致**（dev 実測）。つまり catchup も認証を正しく通し、
  401 で空振りせずに本当に2回起動する
- `message-sender` に排他が無い。「対象を読む → LINE に push → `confirm_status` を 'sent' に更新」
  の間に await が複数挟まる
  （`supabase/functions/message-sender/index.ts:177-184, 252-262, 366, 371-375`）。
  リポジトリに advisory lock / 行ロックは存在しない

→ **`confirm_status` による重複防止は「逐次実行なら有効・同時実行なら無効」**。
付記2 のコメントはこの区別を欠いていた。

### 施した対策（`supabase/migrations/20260825040000_fix_catchup_schedule_collision.sql`）

catchup の発火分を **:15 と :45** に移した（`15,45 0-12 * * *`）。
`:00` に発火する既存ジョブと分単位で重ならなくなる。カバー範囲は変わらない。

あわせて、この種のバグを二度と入れないための機械検査を追加した
（`scripts/v11/check-cron-no-collision.ts`、判定の条件4c）:
**message-sender を叩く active な cron ジョブの「1日の発火分」集合を求め、
どの2本も交わらないことを確認する。**
この検査は、修正前の dev に対して実際に `01:00` の衝突を検出して落ちることを確認してある。

### これでは不十分（朝に判断してほしいこと）

**分をずらすのは衝突の確率を消すだけで、競合そのものは残る。**
1回の実行が15分以上かかれば次の catchup と重なりうる。根本的な直し方は
`message-sender` 側の **claim-then-send**:

「`participants` の `confirm_status` を `pending` の行に限って `sent` へ更新し、
**1行更新できたときだけ** push する」という順序に変える。
（現状は push が成功した後に `sent` へ更新している。）
これなら同時実行でも1回しか送られない。

検討が必要なのは「push が失敗したとき `pending` に戻すか」。戻すと再送の余地が生まれ、
戻さないと取りこぼす。既存コードは push 成功後に更新する順序なので、
現状は「送れなかった人は次回また対象になる」側に倒れている。
claim-then-send にすると既定の倒れ方が逆になるため、**運用上どちらが望ましいかの判断が必要**。

### 【2026-08-25 追記】claim-then-send は実装・デプロイ済み。実地で検証された

上記の claim-then-send を実装し、dev にデプロイした（`supabase/functions/message-sender/index.ts`）。
push の**前**に「`pending` の行に限って `sent` へ更新」し、**1行更新できたときだけ** push する。
UPDATE が行ロックを取るので、同じ participant を2つの実行が同時に確保できない。
push が失敗したら `pending` に戻して次回再試行させる（「届かない」方が「2通届く」より
損害が大きいという判断）。個別送信モード（送り直し）は `confirm_status` を無視する仕様なので
claim を掛けていない。

**実地での検証（仕込みではなく本物の競合）:**

`confirm-broadcast-catchup` の発火（`00:15:00.050Z`）と手動起動（`00:15:00.362Z`）が
**312ms 差で重なった**。結果:

| 実行 | 応答 |
|---|---|
| cron 側 | `{"status":"ok","skippedConcurrent":1,"targets":1,"sent":0,"failed":0}` |
| 手動側 | `{"status":"ok","skippedConcurrent":0,"targets":1,"sent":1,"failed":0}` |

cron は対象1件を pending として**読めた**が、claim に失敗して push せず終了した。
**push は合計1回**。claim-then-send が無ければ両方が push し、同じ確認メッセージが2通
届いていた。`skippedConcurrent` はレスポンスとログに出るので、配信ジョブが同一分に
重なっていることに運用で気づける。

なお `notification_logs` にも `kind='confirm_broadcast' recipients=1 sent=1 failed=0
skipped_no_line_id=1` の行が残った（参加者本人への配信が計測対象になったのは初めて）。

## 付記4: PRレビューで見つかった8件と、その直し方 — 2026-08-25

セルフレビューではなく人によるコードレビューで、**8件すべて妥当な指摘**が出た。
特に「合格条件がプロダクトの正常な成長と排他になっている」型の欠陥が、
夜間に2度直したはずなのに**まだ3箇所残っていた**。記録して残す。

### 二重送信（medium）

**`pushMessage` は毎回 `crypto.randomUUID()` を `X-Line-Retry-Key` に入れていた。**
これは LINE 側から見ると常に「別の初回リクエスト」で、冪等性の仕組みが完全に無効だった。

claim-then-send は push 失敗時に `pending` へ差し戻して再試行させるが、`pushMessage` は
「LINE は受理したがレスポンス受信前に接続が切れた」場合にも throw する。
キーがランダムだと、その再試行が別送信として受理され**利用者に2通届く**。
差し戻すか戻さないかのどちらを選んでも事故が起きるコイントスになっていた。

LINE 公式ドキュメント "Retrying an API request" で確認した仕様:

- 値は16進 UUID 形式
- 初回リクエストから **24時間** 保持される
- 同じキーで再送すると **409 Conflict** が返り、**重複配信されない**
- ヘッダ無しで送った初回リクエストは、後からリトライできない

対応:

- `_shared/line/retry_key.ts` を追加。送信意図（用途・participant_id・event_id）から
  SHA-256 で決定的に UUID を導出する
- `pushMessage` に任意の `retryKey` 引数を追加（未指定なら従来どおりランダム＝`notifier` は挙動不変）
- **409 を成功として扱う**分岐を追加。これが無いと「実際は届いたのに失敗扱い→また差し戻し」を
  繰り返し、24時間の保持期間を過ぎたところで本当に重複する

残る限界: 24時間を超える再試行は重複しうる。確認配信は同日中に完結する運用なので受け入れる。

### 「合格条件が正常系と排他」型の欠陥がさらに3件（medium）

| 検査 | 何が起きていたか |
|---|---|
| 条件4 | 「どの行も宛先1名以内」を要求していた。`message-sender` は**1イベント1行に集約**する設計なので、リンク済み参加者が2名いる本番イベントでは `recipients=2` の行が生まれ**恒常的に落ちる** |
| 条件1 (`scraped_at`) | 対象 epu の**全行**に更新を要求していた。scraper は今回のスクレイプに存在した行しか upsert しないので、**参加者が1名離脱した時点から以後すべての実行で落ちる** |
| 条件1 (`notification_logs`) | 「2回目ポーリング前後で今日の行数が変化しない」を全 kind で見ていた。同じPRで足した catchup cron が約40秒の窓に割り込むと**偽陽性で落ちる** |

対応:

- 条件4は「宛先数の上限」をやめ、**`sent <= recipients` の整合**と
  **同一イベント・同一日に `confirm_broadcast` が1行だけ（= fan-out していない）**を測る形にした。
  `oa_members` の紐付け数チェックも合否から外した（件数は運用で変わる）
- `scraped_at` は「更新された行数 == scraper 応答の `count`」で判定。
  据え置きの行は離脱者として区別してログに出す
- `notification_logs` の件数は `kind='scrape_changes'` かつ当該イベントに絞る

### 監査ログの欠落（low）

全件が同時実行に先を越されると `targetResults` が空になり、`notification_logs` に1行も残らなかった。
**重複実行を可視化するために足したログが、まさに重複実行のときだけ効かない**状態だった。
先を越された対象も結果として積み、`detail.skipped_concurrent` に件数を残す形にした。
あわせて `recipients = sent + failed + skippedConcurrent` が成り立つようにして、
レスポンスの `targets` との食い違いも解消した。

### `/login` の静的レンダリング退行（low/medium）

`useSearchParams` を満たすためにページ**全体**を `<Suspense>` で包んでいたため、
Next.js がサブツリー全体で静的レンダリングを bail out し、`/login` のプリレンダー HTML が
実質空になっていた（フォームはハイドレーション後にしか現れない）。

実測で確認: **修正前 9,178 bytes で `<form>` を含まず、修正後 13,849 bytes で含む**。

`useSearchParams` を読むだけの小さな子コンポーネントだけを `<Suspense>` の内側に置き、
フォームは外に戻した。

### 一時的な `declined` が戻らないことがある（low）

`send-one-real-message.ts` は participant を `declined` に書き換えたあと、
後続の scraper 呼び出しがライブページから復元してくれることに依存していた。
その呼び出しが失敗すると復元パスが無く、`get_confirm_targets` は `status='attending'` を
要求するのでその参加者は静かに対象から外れ、**条件1bが無関係に見える理由で落ちる**。
`try/finally` で元の status を必ず書き戻すようにした。

### ポーリング cron の platform フィルタ漏れ（low）

ジョブ名もコメントも Twipla 前提なのに、ファンアウトの select は `event_platform_urls` を

`cron.job_run_details` は `succeeded` のままで、**この無駄打ちは何にも表面化しない**。
`20260825050000` で `and epu.platform = 'twipla'` を足した。

### この修正で分かったこと

`unschedule` + `schedule` でジョブを作り直すと **jobid が変わり、過去の発火履歴が
現在のジョブに紐付かなくなる**。条件3は「*いまの*ジョブが実際に動いた証拠」を要求するので、
マイグレーションでジョブを差し替えた直後は正しく落ちる。
証拠を作り直すために `set-test-event-window.ts` に `poll` モードを足した
（`confirm_days_before=0` かつ2日後にすることで、**ポーリングだけ有効・確認配信は無効**にできる。
LINE を1通も送らずに cron の実発火証拠を作れる）。

## 付記5: 離脱者（ページから消えた参加者）の検出 — issue #2 / 2026-08-31

### 何が抜けていたか

`diffParticipants` は `incoming`（今回のスクレイプ結果）をループするだけだったので、
**既存にあって今回現れなかった参加者が完全に不可視**だった。

Twipla では参加を取り消すと**行そのものがページから消える**。これはセクション間の移動
（attending → declined）とは別の変化で、次の3つの穴を生んでいた。

1. 主催者に「減った」ことが通知されない（増加は `new` として通知される）
2. DB の行は `attending` のまま残り、`get_confirm_targets` が**もう来ない人を
   確認配信の対象に含め続ける**
3. `scraper` は行を削除しないので `scraped_at` も古いまま据え置かれる
   （PRレビューで、条件1の `scraped_at` チェックが「全行の更新」を要求していたために
   離脱者が1名出た時点で恒常的に落ちる問題として表に出た）

### 表現の選択: `status='left'` を足す

`departed_at` 列を足す案と比較して、**新しい status 値**を選んだ。

決め手は `get_confirm_targets` が cron モード・手動モードのどちらも
`p.status = 'attending'` で絞っていること（`20260612120000:53,85`）。
離脱者を `'left'` にすれば、**その関数を一切変えずに配信対象から外れる**。
`departed_at` 列だと両分岐に条件を足す必要があり、message-sender の挙動に影響する
変更の範囲が広がる。admin 側も `participants.status` のラベル表を持っていないため
UI 変更は不要で、ダッシュボードの `status='attending'` カウントは離脱者が外れて
**むしろ正確になる**。

副作用として `status` が「ページのどのセクションに居たか」と「もう載っていない」を
兼ねることになるが、`status` を「最後に観測した状態」と読めば一貫している。

マイグレーション: `20260831120000_add_left_participant_status.sql`

### 誤検知への2段の防御

離脱の誤記録は「全員が確認配信の対象から外れる」という最悪の失敗につながるので、
検出と適用を分けた。

1. `sectionCount === 0` のHTML（マークアップ変更・エラーページ等）は
   scraper が**取得失敗として早期 return** する（2026-08-25 の防御）
2. `shouldApplyDepartures`（純関数）が **「既存が居るのに今回0件」なら適用しない**。
   イベントが本当に全員取り消しになることは有り得るが、その頻度よりスクレイプ異常の
   頻度の方が高く、誤って全員を外す損害の方が大きいと判断した

**割合しきい値は設けていない。** 「10名中9名減ったら怪しい」という判定は、
正当な離脱を黙って無視する新しい穴になる。代わりに件数をレスポンス・ログ・通知に
出して運用で気づけるようにした。

また、既に `'left'` と記録済みの行は離脱として再検出しない
（毎回のポーリングで同じ人を離脱として通知し続けないため）。
離脱者が戻ってきた場合は `left → attending` の statusChange として扱われる。

### 通知

`buildScrapeChangesNotification` に参加取消の件数を足した。

```
【イベント名】参加者情報が更新されました（新規N名・出欠変更N名・参加取消N名）
```

離脱だけが起きた場合も通知が飛ぶ（以前は `new` と `statusChanged` が両方0なら
通知そのものがスキップされていた）。

### dev での実証

実ページに存在しない参加者を1行仕込んでポーリングを走らせた（イベントは通知窓の外なので
LINE は飛ばない）。

```
scraper 応答: {"count":2,"saved":true,"changes":{"new":0,"statusChanged":0,"departed":1},"notified":0}
DB: 仕込んだ行の status='left'
実在する参加者2名: left にされていない
notification_logs: 11 → 11（送信ゼロ）
```

### 副産物: 条件3の証拠が古びる問題を直した

条件3（cron が実際に scraper を叩いた証拠）は、直近N件の実行履歴をスキャンして
`return_message` が `'0 rows'` でない行を探していた。ポーリング対象が無い期間は
15分ごとに `'0 rows'` が積まれるため、**証拠は数日で窓から押し出される**。
実際に約600回の `'0 rows'` に押し流されて条件3が落ちた
（3周目の独立検証役が「近いうちに WARN 経路に落ちる」と予言していた箇所）。

件数スキャンではなく**全履歴に対する存在確認**（`return_message ~ '^[1-9][0-9]* row'`）で
拾うようにした。

### 残る論点

- 確認配信を既に送った人（`confirm_status='sent'` 以降）が離脱した場合、1問1答の
  進行中セッションはそのまま残る。回答が返ってくると保存される。
  実害は小さいと判断して触っていないが、整理するなら別途
- 離脱者が戻ってきたとき `confirm_status` はリセットしていないため、既に配信済みの人には
  再送されない。これは意図した挙動（同じ確認を2回送らない）
