# v1.1 主催者向け通知が本番で0件届いている理由 — `oa_members.line_user_id` 未設定問題

## 要約（3行）

主催者向け通知が本番で一度も届かないのは、**「主催者が自分の LINE を `oa_members.line_user_id` に紐付ける」経路がコード上どこにも存在しない**ため。owner 登録（`register_owner_by_identity()` / `setup-prod-member.ts`）は X 照合だけで行を作り、`line_user_id` 列には一切触れない。dev で届くのは `setup-dev.ts` が固定値を UPDATE で直接埋めているだけで、prod にはこの UPDATE に相当する処理が存在しない。

## 1. 結論

本番で `notification_logs` が全件 `sent:0` なのは、`notifier.ts` が受信者を `oa_members.line_user_id != null` から解決する構造（`supabase/functions/_shared/notify/notifier.ts:118-152`, `280-315`）に対して、**`oa_members.line_user_id` を書き込むコードが prod 側に一つも実装されていない**ためである。バグではなく、機能未実装（導線の欠落）。

owner 行自体は2つの経路（`register_owner_by_identity()` RPC / `setup-prod-member.ts`）で作られるが、両方とも X の `screen_name` 照合のみを行い、`line_user_id` 列は `insert` 文の対象列に含まれていない（`supabase/migrations/20260611171038_enable_rls.sql:290-296`、`scripts/setup-prod-member.ts:49-59`）。つまり prod の `oa_members` 行は「LINE 通知の受信者」としては生まれた瞬間から永久に空である。

## 2. `oa_members.line_user_id` を埋める経路の全数調査

`grep -rn "oa_members" --include="*.ts" --include="*.sql" /Users/kugyu10/work/nomimas-bot` で洗い出した、`oa_members` に書き込む（INSERT/UPDATE する）全箇所:

## 3. なぜ dev では届いて prod では届かないのか

### データの差
- dev: `oa_members` 4行のうち user1×dev-oa owner の1行だけ `line_user_id = 'U0000...ownr1'`（架空値）が入っている。これは `setup-dev.ts:246-256` の UPDATE 文が seed 時に直接書き込んだもの。user2 の行はコメントに明記の通り「`skipped_no_line_id` 経路の検証用」に意図的に null のまま残されている（`scripts/setup-dev.ts:20`）。
- prod: `oa_members` 2行、`line_user_id` は0行が非null。owner 行は #1 か #2 の経路（X 照合）で作られたはずだが、いずれも `line_user_id` を書く列を持たない INSERT のため、生成された瞬間から null のまま。

### コードの差
- dev には「テストのために架空の LINE userId を直接 DB に書き込む」スクリプト（`setup-dev.ts`）がある。これは E2E テスト用の**踏み台**であり、実際の運用導線（「主催者が本当に自分の LINE を紐付ける」フロー）を代替するものではない。
- prod にはこの踏み台に相当する「本物の LINE userId をどこかから取得して `oa_members` に書く」処理が一切実装されていない。owner 登録（X 照合）と LINE 紐付けは、コード上完全に別の関心事として扱われており、両者をつなぐ処理が欠落している。

つまり dev が「届く」ように見えるのは、実データフローではなく **テスト用のショートカットが本番相当の状態を偽装している** ためであり、prod は最初から「主催者の LINE userId を知る手段がない」状態にある。

## 4. 直し方（選択肢と推奨）

### 案A: ワンショットのセットアップスクリプトで prod の `oa_members.line_user_id` を埋める

- **仕組み**: `import-prod-line-followers.ts` は既に「LINE の友だち一覧を取得して `line_users` に upsert する」処理を持つ（`getFollowerIds` → `getProfile` → `line_users` upsert、`scripts/import-prod-line-followers.ts:67-148`）。ただし取得した LINE userId が「誰の」ものかは分からない（表示名しか付かない）。主催者を特定するには、主催者本人が OA を友だち追加した上で何かメッセージを送信してもらう必要がある。そうすれば webhook の message ハンドラが `line_users` に登録する（`supabase/functions/webhook/index.ts:493-524`）。その後、人間が `line_users` の表示名を見て「これが主催者の行だ」と目視で特定し、その `line_users.line_user_id` を `oa_members.line_user_id` に UPDATE する1回限りのスクリプト（`setup-prod-member.ts` に似た構造で新規作成、または既存スクリプトに追記）を書いて流す。
  - 具体的な手順:
    1. 主催者に「OA を友だち追加して何か一言送ってください」と依頼する
    2. webhook 経由で `line_users` に行ができるのを確認する（`select * from line_users where oa_config_id=...`）
    3. 新規ワンショットスクリプト（例: `scripts/setup-prod-owner-line.ts`）で `update oa_members set line_user_id = (該当 line_users.line_user_id) where oa_config_id=... and role='owner'` を実行する
- **主催者の手間**: 友だち追加＋一言送信のみ（既にやっている可能性が高い）
- **実装コスト**: 新規スクリプト1本（`setup-prod-member.ts` を土台に流用可能、数十行）。DB 接続とガード（PROD_PROJECT_REF 確認）は既存パターンをコピーすればよい
- **危険**: 「主催者本人の行」をどう特定するかが手動（displayName の目視確認）になる。OA の友だちが主催者以外にもいる場合、誤って別人に紐付けるリスクがある（人数が少ない今のうちは実害小さい）

### 案B: webhook で自動化する（follow / message イベント発火時に判定して自動で埋める）

- **仕組み**: follow/message ハンドラで、その LINE ユーザーが「そのOAの主催者本人」だと判定できれば、自動的に `oa_members.line_user_id` を埋められる。
- **判定材料の有無を確認した結果**: follow イベントのペイロードには `event.source.userId` と `oa_config_id`、任意で `profile.displayName` しかない（`supabase/functions/webhook/index.ts:208-244`）。message イベントも同様（`:493-524`）。**LINE 側のイベントには「このユーザーが主催者かどうか」を示す情報が一切含まれない**（LINEアカウントとXアカウント/Supabase authユーザーを紐付ける手がかりがコード上どこにもない）。`oa_configs.admin_twitter_id` はXのscreen_nameであり、LINEのuserIdとは異種の識別子で、webhookペイロードから両者を自動で結びつける方法はない。
  - **したがって案Bは判定材料が無いため不可**。何らかの追加ステップ（例: 主催者だけが知る合言葉をLINEで送ってもらい、それをトリガーにする等）を導入しない限り、自動判定はできない。これは推測ではなく、webhook のイベントスキーマ（`supabase/functions/webhook/index.ts` のペイロード定義、ファイル冒頭の型定義含む）を読んだ上での確認結果。

### 案C: 管理画面に紐付け UI を足す

- **仕組み**: ログイン中のユーザー（`oa_members` の行の持ち主、つまり `auth.uid()` に対応する行）が、自分の LINE を紐付ける画面を管理画面に追加する。既存の参加者紐付け UI（`admin/components/events/linking-tab.tsx` + `admin/lib/actions/linking.ts`）は `participants.line_user_id` を更新する構造で、対象が `participants` テーブルである点が異なる。同じ「`line_users` から選んで紐付ける」UIパターン（コンボボックス選択 → server action で UPDATE）を転用し、更新先を `oa_members`（自分の行のみ、`auth_user_id = auth.uid()` で絞る）に変えれば実装できる。
  - 具体的に触るファイル: `admin/lib/actions/linking.ts` に相当する新規 action（例: `admin/lib/actions/oa-line-link.ts`）、`admin/components/oa/` 配下に紐付けUIコンポーネントを新設、`admin/app/(app)/oa/settings/page.tsx` に組み込み。現状 `admin/lib/actions/oa.ts` / `admin/components/oa/oa-settings-form.tsx` / `admin/lib/schemas/oa.ts` には `line_user_id` / `oa_members` への言及は一切ない（grep 確認済み）ため完全新規実装になる。
  - **RLS の課題**: `supabase/migrations/20260611171038_enable_rls.sql:151` のコメントに「`oa_members` には書込ポリシーを追加しない（RPC経由のみ登録）」とあり、`authenticated` に直接 UPDATE 権限を与えていない。UI から書くには `register_owner_by_identity()` と同様に SECURITY DEFINER の RPC（例: `link_own_line_user(line_user_id uuid)`）を新設し、`auth.uid()` が所有する行のみ更新可能にする必要がある。マイグレーション追加が必須。
- **主催者の手間**: 管理画面にログインして、自分のLINE表示名をリストから選ぶだけ（LINE友だち追加＋一言送信は前提として必要）
- **実装コスト**: 中（新規マイグレーション + RPC + server action + UIコンポーネント + 画面組み込み）
- **危険**: 新規 RLS ポリシー/RPC の設計を誤ると、他OAの`oa_members`を書き換えられる脆弱性になりうる（`with check` で `auth_user_id = auth.uid()` を必須にすること）

### 推奨

**案A（ワンショットスクリプト）を今すぐ、案C（管理画面UI）を並行して着手する。**

理由: 案Aは今夜〜翌朝すぐに「主催者に1回だけ届く」状態を作れる最短経路で、既存の運用スクリプト（`setup-prod-member.ts`）と同じパターンの流用で済み、新規マイグレーションが不要。案Cは再現性・今後増える主催者向けに必要だが、RLS変更を伴うためレビューに時間がかかる。案Bは判定材料が無いため却下。

## 5. これを直すと何が観測できるようになるか

- `notification_logs` の `recipients` が2件中1件以上で non-zero になり、`sent` も non-zero になる（現在は `recipients` 自体も常に0 — `notifier.ts:150-152` の `recipientMembers.filter` が空集合になるため）
- `skipped_no_line_id` は「まだ紐付けていない co-owner の人数」という意味に変わる。現在は「主催者全員が未紐付け」を示す値（prodでは常に `allMembers.length` と同数）だが、紐付け後は「owner のうち紐付け済みでない人数」という本来の意味（dev の user2 が示す設計意図）に一致する
- push 送信が実際に発火するため、LINE API のレート制限やエラー（`notifier.ts:183-188` の per-target try/catch）が初めて実運用で観測可能になる
