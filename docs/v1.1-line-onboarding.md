# v1.1 LINE友だち→participants自動紐付け 調査メモ

**要約**
- 現状「LINE友だち追加」と「Twipla参加者行」を結ぶ橋は存在しない。手動UIか、過去に手動で結んだ同一screen_nameへの引き継ぎ（`propagate_oa_links`）しかない。
- LINEの公式follow eventにURLパラメータやreferral情報は乗らない（案A＝友だち追加URL+パラメータは技術的に不可）。
- 推奨は**案B（合言葉＝Xアカウント名を本人にLINEで送らせる）＋確認クイックリプライ**。既存webhookのmessageハンドラを拡張するだけで済み、LINE側の設定変更が不要。

## 1. 現状の紐付け機構（事実のみ）

### LINE側から人が来たとき何が起きるか

- **follow イベント**: `line_users` へ `(oa_config_id, line_user_id)` をUPSERT。表示名を Profile API で取得できれば保存するが、それ以外の情報（X screen_name等）は一切受け取らない。participants テーブルには触らない。
  `supabase/functions/webhook/index.ts:208-247`
- **message イベント**（直近コミット `46ec76d feat(webhook): message イベントでも line_users を登録`）: follow を受け取れなかった既存友だち向けの取り込み経路として、message受信時にも同様に `line_users` へUPSERTする。その後は「進行中(`sent`/`in_progress`)の participant がいれば現在の質問を再送するだけ」で、participants への新規紐付けは一切行わない。
  `supabase/functions/webhook/index.ts:493-583`（UPSERT: 501-523、再送のみ: 539-582、「answers / participants を書き換えない（仕様）」と明記: 581）
- **postback イベント**（1問1答の回答）: `participants.line_user_id` が既に入っていることが前提。入っていなければ「なりすましチェック不可 → 保護的に無視」して終了する。つまり postback 経路は紐付け未完了の人を救えない。
  `supabase/functions/webhook/index.ts:288-294`

### participants.line_user_id が入る経路（現在3つ）

1. **管理画面の手動紐付けUI**（ADMIN-02）: `admin/components/events/linking-tab.tsx` のコンボボックスで、未紐付け participant に line_users を1件ずつ選んで紐付ける。Server Action は `admin/lib/actions/linking.ts` の `linkParticipant()`。
2. **`propagate_oa_links(oa_config_id)`**（DB関数、`supabase/migrations/20260612120000_setup_cron_and_targets.sql`）: 同一OA内で「既にどこかのイベントで手動紐付け済みの screen_name」を、同OAの**別イベントの未紐付け participants**にも自動で引き継ぐ。screen_nameを小文字化して一致判定し、`line_user_id is null` の行だけを更新する（既存の紐付けは上書きしない）。呼び出し元は2箇所:
   - スクレイプ後（`supabase/functions/scraper/index.ts:142-155`）
   - 手動紐付け直後（`admin/lib/actions/linking.ts:57-68`、手動リンクの副作用としてbest-effort実行）
3. 上記1で最初の一人が紐付けられた後、2が水平展開する——という構造。**「誰も一度も手動で紐付けていないscreen_name」を1から自動で紐付ける経路は存在しない。**

本番の participants 16人が全員紐付け済みなのは、主催者が最初に手動でUI操作した結果を `propagate_oa_links` が横展開した/繰り返しただけで、初回の人力作業は毎回必要という点は変わっていない。

### 自動で紐付かない理由（決定的に欠けている情報）

`line_users` テーブルは LINE の `userId`（"U..." 文字列）と `display_name`（LINE表示名）しか持たない。
`supabase/migrations/20260611171037_create_core_tables.sql`（line_users定義部）

`participants` テーブルは Twipla の `screen_name`（Xアカウント名）と `display_name`（Twipla上の表示名）しか持たない。
`supabase/migrations/20260611171037_create_core_tables.sql`（participants定義部、natural_keyのコメント参照）

この2つのテーブルを繋ぐ列・値は**どこにも存在しない**。LINEのfollowイベントはXアカウント名を一切運ばず、TwiplaのスクレイプもLINE userIdを一切知らない。つまり「LINE側の人」と「Twipla側の行」を機械的に同一人物と判定するための橋（共通の識別子、または本人による自己申告）が構造的に欠けている。これが手動UIが必須になっている根本原因。

## 2. 導線の選択肢

### 案A: イベントごとの友だち追加URL + パラメータ

**仕組み**: LINEの友だち追加URLにイベント識別子をクエリパラメータ等で載せ、follow イベント側でそれを受け取って紐付ける。

**LINE仕様上の可否**: **不可**。LINE Messaging APIのWebhook Event Objects共通仕様（type / mode / timestamp / source / webhookEventId / deliveryContext）とfollow event固有のフィールド（replyToken / follow.isUnblocked）以外に、友だち追加時に踏んだURLのクエリパラメータや参照元（referral）を運ぶフィールドは無い（公式ドキュメント `developers.line.biz/en/reference/messaging-api/` のFollow event定義を確認。ただし今回のWebFetch取得内容は一部欠落しており全文の目視確認はできていない——一般に知られている仕様と矛盾しないという意味での確認であり、完全な断定はしない）。友だち追加URL自体はLINE公式アカウントごとに固定の1つしか持てず、URL側にクエリを付けても follow イベントの `source.userId` 以外の情報は一切サーバーに届かない。
**結論**: 「イベントごとに違う友だち追加URLを発行し、followイベントでイベントを識別する」という設計は成立しない。

（参考: LINE Loginと連携した `bot_prompt` パラメータ経由の「友だち追加オプション」は別物で、これは案C/案Dの方に関係する——後述）

### 案B: 合言葉方式（Xアカウント名を本人にLINEで送らせる）

**仕組み**: 友だち追加後、本人に「あなたのXアカウント名（@screen_name）を送ってください」と促し、message イベントで受け取ったテキストと同OA内の未紐付け `participants.screen_name`（大文字小文字を無視して比較。既存の `propagate_oa_links` と同じ比較ロジック）を照合する。一致したら該当participant（同screen_nameの全イベント分、propagate_oa_linksと同じ横展開込み）に `line_user_id` をセットする。

**参加者の手間**: 友だち追加後にテキスト1行送るだけ。
**主催者の手間**: 「友だち追加後にXアカウント名を送ってください」という案内文を greeting_message（既存の定型文設定）に書く程度。個別作業はゼロになる。
**取りこぼしのしかた**:
- screen_nameの表記（先頭`@`の有無、`x.com/`付きURLで送る等）のばらつき → 正規化処理が必要（プレフィックス除去・小文字化程度は容易）。
- 同OA内に同名screen_nameが複数イベントに渡って複数存在する場合の扱いは既存の `propagate_oa_links` と同じ挙動（distinct on lower(screen_name) + updated_at desc採用）を踏襲すればよい。
- **なりすましリスク**: Xアカウント名は基本的に公開情報（Twiplaの参加者一覧に載っている）なので、「その人の名前を知っている別人」が先に自分のLINEを紐付けてしまうと、本人の代わりに最終確認の質問に回答されたり、集合場所・参加費などのイベント詳細を横取りされる可能性がある。現行の手動UIも原理的には同じリスクを持つが、主催者の目視判断というワンクッションがある分、完全自動化はこのクッションを失う。
  → 対策として「送られてきたscreen_nameに一致するparticipantのdisplay_nameを引用し、『◯◯さんで間違いないですか？』とQuick Replyで確認を取ってから確定する」という一段階を挟むのが最小限の緩和策（実装コストは小さい）。
**実装コスト**（ファイルレベル）:
- `supabase/functions/webhook/index.ts` の message ハンドラ（493-583行）に分岐追加: 既存の「進行中participantへの再送」ロジックの前に「未紐付けparticipant向けのscreen_name照合」を追加。
- 新規SQL関数（例: `link_by_screen_name(p_oa_config_id, p_line_user_uuid, p_screen_name)`）を `propagate_oa_links` と同様の書式でマイグレーションに追加。既存ロジックの再利用がしやすい。
- `supabase/functions/_shared/confirm/messages.ts` に確認応答用のメッセージビルダーを追加。
- `admin` のOA設定（greeting_message）に案内文を書く運用対応のみで、admin側のコード変更は不要。

### 案C: Xアカウント連携（管理画面の既存X OAuthを参加者側にも使う）

**仕組み**: 現在 `admin/app/login/page.tsx` にある `supabase.auth.signInWithOAuth({ provider: "x" })` は**主催者ログイン用**（`auth.users` / `oa_members` と紐づく）であり、参加者はそもそも `auth.users` に登録されない前提の設計になっている。参加者向けに転用するなら、参加者専用の匿名/軽量な認証フロー（別のSupabase Auth設定、または参加者専用テーブルへのX OAuthトークン保存）を新設する必要がある。

**参加者の手間**: Xログイン1回（が、LINEの友だち追加とは別のブラウザ操作が挟まるため、案Bよりステップが1つ多い）。
**主催者の手間**: ほぼゼロ（案B同様に自動化される）。
**取りこぼしのしかた**: X側のログイン許可が必要なため、Xアプリを開かない/ログインを嫌う参加者は脱落する。ブラウザとLINEアプリを往復する導線になるため離脱率は案Bより高いと想定される（未検証）。
**実装コスト**: 既存の管理者向けX OAuth実装（`admin/app/login/page.tsx` とその後続の `/auth/callback` 処理）は「ログイン=主催者用ユーザーの作成/紐付け」を前提にしているため、参加者向けに転用するには実質的に別経路（別チャネル設定、別テーブル、別コールバック）を新規に作ることになり、後述の案Dとほぼ同等の実装量になる。参加者が「Webページ経由」で操作する点も含めて、案Dの一形態と捉えるのが正確。

### 案D: 主催者がTwiplaのイベント説明文に貼る短縮URL + Webの中間ページ

**仕組み**: admin（Next.js）に参加者向けの1枚ページ（例: `/join/[eventId]`）を新設。そこでXアカウント名を入力（または案Cのように X OAuthで本人確認）させてから、LINE友だち追加ボタンに遷移させる。中間ページ側でイベントIDと入力されたscreen_nameを一時テーブルやトークン付きURLに保存しておき、その後の友だち追加（follow）やmessage送信と突き合わせる。

**参加者の手間**: Webページを開く→（X連携する場合はログイン）→LINE友だち追加、の複数ステップ。
**主催者の手間**: イベントごとに中間ページのURLをTwiplaの説明文に貼る作業が発生（現状のTwipla URL登録作業に1つ追加されるだけなので大きな負担ではない）。
**取りこぼしのしかた**: 中間ページを経由せず直接LINEの友だち追加URLから来た人（既存友だちがそのまま残っている場合や、URLを共有された場合）は捕捉できない。ページ→LINEの間でブラウザを閉じる/離脱するとその回の申告が失われる。
**実装コスト**（ファイルレベル）: `admin/app/` に新規ルート（例 `join/[eventId]/page.tsx`）、その入力を一時保持するテーブルまたはstateパラメータ付きlink生成、followイベント側でその一時データと突き合わせるロジックの追加。案Bと比べて「新しい参加者向けWebページ」「一時データの保存と有効期限管理」「LINE友だち追加後にどうやってその一時データと突き合わせるか（結局follow eventにはパラメータが乗らないので、時系列で最も近い一時申告とマッチさせる等の推測ロジックが必要）」という新規要素が多い。

### 案E: LINE Login連携（bot_prompt）による本人確認つき友だち追加（参考・高コスト）

**仕組み**: LINE Login チャネルをMessaging APIチャネル（OA）と同一プロバイダ内でリンク設定し、LINE Loginの認可URLに `bot_prompt=normal|aggressive` を付けてWebページから遷移させる。LINE公式ドキュメント（`developers.line.biz/en/docs/line-login/link-a-bot/`）によれば、これによりログイン画面内（または直後の別画面）で「このLINE公式アカウントを友だち追加しますか」という選択肢を提示できる。リンクされたOAとLINE Loginチャネルの間でuserIdが一致するかどうかは、ドキュメント上で明言されている箇所を今回のWebFetchでは確認できなかった（**未確認**）。

**実装コスト**: LINE Developersコンソールでの新規チャネル作成＋リンク設定（コード外の設定変更）、案Dと同様のWebページ、LINE Login SDK/OAuthフローの実装一式。現状のコードベースに何もない状態から積む必要があり、最も工数が大きい。

## 3. 推奨

**推奨: 案B（合言葉方式）＋ 確認クイックリプライの追加**

**なぜこれか**:
- LINE側の設定変更が一切不要（チャネル追加・リンク設定・新規ドメインの用意が要らない）。
- 実装が既存コードの延長で済む。message イベントで `line_users` をUPSERTする経路（`webhook/index.ts:501-523`、直近で追加済み）と、screen_name一致による横展開ロジック（`propagate_oa_links`、既に本番で動いている）という2つの部品がすでにあり、これらを繋ぐだけで良い。新規テーブルもほぼ不要。
- 参加者の手間が「テキスト1行送る」のみで、LINEアプリ内で完結する（ブラウザ往復が要らない）。

**なぜ他を却下したか**:
- 案A: LINEの仕様上そもそも不可能（follow eventにパラメータが乗らない）。
- 案C/D/E: いずれも「参加者向けのWebページ」または「新規LINE Loginチャネルのコンソール設定」を必要とし、実装量・運用コストが案Bより明確に大きい。今回の"実運用2ヶ月で見えてきた実感を踏まえた軽量なv1.1"という文脈（`.claude/.../memory/nomimas-v11-direction.md` 相当のメモにある「GSD離脱」の方向感）に対して、コストに見合うリターンが今は無い。将来、なりすましリスクを本格的に潰したくなった時点で案D/Eへ拡張する余地は残せる。

**最小実装（ファイル名レベル）**:
1. `supabase/functions/webhook/index.ts` — message ハンドラ内、`line_users` UPSERT（501-523行）の直後に「未紐付けparticipant照合」分岐を追加。既存の「進行中participant再送」ロジック（539-582行）とは排他（紐付け済みなら再送、未紐付けならscreen_name照合、を優先度づけて分岐）。
2. 新規マイグレーション — `propagate_oa_links` を参考にした `link_by_screen_name(oa_config_id, line_users.id, 入力テキスト)` 関数（1件ずつの紐付け＋propagate_oa_linksの呼び出しをセットで行う）。
3. `supabase/functions/_shared/confirm/messages.ts` — 「◯◯さんで間違いないですか」の確認クイックリプライメッセージビルダーを追加。
4. `supabase/functions/_shared/confirm/postback.ts` / `state.ts` — 確認クイックリプライのYES/NO postbackをデコードして確定/やり直しさせる小さな分岐（既存のpostback decode/handle処理に相乗り）。
5. 運用対応（コード外）: OA設定の `greeting_message`（管理画面から編集可能・コード変更不要）に「友だち追加後、あなたのXアカウント名（@から始まる文字列）を送ってください」という案内文を追加。

## 4. 実装しないと決めた理由 / 前提条件

今夜は調査のみで実装しない。朝、本人が決めるべき論点:

- **参加者に何を要求してよいか**: 「Xアカウント名を自己申告させる」で足りるか、なりすまし対策として確認クイックリプライ（案Bの緩和策）を必須にするか。確認ステップを入れると1問1答フローのステートマシン（`_shared/confirm/state.ts`）に「紐付け確認」という新しい状態を割り込ませる必要があり、既存のconfirm_status（pending/sent/in_progress/completed）のどこにこの新状態を挟むか設計判断が要る。
- **LINE OAの設定変更が必要か**: 案B/案Aの結論を採るなら**不要**。案D/Eに進む場合はLINE Developersコンソールでの新規チャネル作成・リンク設定という、コードの外側の作業が発生する（誰の権限で操作するか含め要確認）。
- **既存の手動紐付けUIをどう扱うか**: 自動紐付けを入れても、失敗ケース（screen_name不一致、確認で「いいえ」を選んだ場合等）の受け皿として `admin/components/events/linking-tab.tsx` の手動UIは残す前提で良いか。
- **なりすまし対策の要否とレベル**: 「Xアカウント名は公開情報だから多少のなりすまし可能性は許容する」という運用判断で良いか、それとも確認クイックリプライを必須にするか、その先（案D/E）まで踏み込むか。
